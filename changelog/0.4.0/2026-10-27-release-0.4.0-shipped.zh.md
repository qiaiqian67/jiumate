# 0.4.0 已发布：Release 出来了，npm 还差一个 token

- **Date:** 2026-10-27
- **Type:** release
- **Scope:** `ci`, `tooling`, `docs`

[English](2026-10-27-release-0.4.0-shipped.zh.md)

`v0.4.0` 这个 Release 现在在 GitHub 上：六个平台的程序包、五个平台的桌面安装包、两个一行安装脚本，以及它们的校验和，都已经发布，`releases/latest/download/<name>` 全部可下载。这一条记录发布链上还剩什么，以及剩的那一样为什么必须在仓库之外。

## 已经在的

**Release 产物。** `v0.4.0` 带 34 个产物：`jiumate-<target>.tar.gz`（linux-x64、linux-arm64、darwin-x64、darwin-arm64、win32-x64、universal）、`jiumate-desktop-*`（两个 macOS 的 dmg 与 zip、win32-x64 的 exe、linux 的 AppImage 与 deb）、`install.sh` 与 `install.ps1`、`latest*.yml` 与 blockmap（自动更新读它们）、两份 `SHA256SUMS`，以及下载清单。

**下载链接。** `releases/latest/download` 这一层是给站点用的：安装包的名字不带版本号，所以一个静态链接永远指向最新的一版。清单里每个产物的名字、大小与 sha256 都对得上；Windows 安装包整份下载下来算出来的 sha256 与公布值一致。

**CI 变绿了。** 21 个 job 全绿，是仓库开张以来第一次。有八个门禁从来没通过过，不把它们修掉，一个 tag 就产不出任何东西：

- **Prettier** 从没被跑过：187 个文件不符合格式，其中一个 `packages/installer` 的渲染器还缺一个闭合的 `div`，Prettier 连解析都做不到。
- **typecheck** 挂在一行上：`writeInspirationCase` 的 `meta` 把 `updatedAt` 声明成 `string`，而 schema 声明的是 `string | null`，而一个 preset 就是以 null 写的。
- **oxlint** 挂在三个把同一个模块 import 两次的文件上——这条规则就是为这件事加的。
- **license** 挂在文档编辑器的字体包上：它的许可证是 `Apache-2.0 AND OFL-1.1 AND LicenseRef-GUST-Font-License`，最后一个没有 SPDX 标识符，它是 GUST Font License，其实际条款是 LaTeX Project Public License 1.3c。三个都是宽松的，而两个字体许可证的义务落在字体文件上，不落在嵌入它的作品上。
- **测试** 挂在 server 分片上，而且是最费劲的一个：108 个测试文件根本没加载，因为分片建的是 core 的依赖树而测的是 server。server 依赖 pets、inspirations 与 skins，core 不依赖，于是这三个从没被构建，套件在跑第一个测试之前就解析不了 `@jadelau/pets`。现在每个测 server 的分片都建 server 的那棵树。
- **Playwright 的浏览器** 没装，五个登录页小人的套件在 `browserType.launch` 处报 "Executable doesn't exist"——这句话读起来像测试坏了，而不是浏览器没装。
- **POSIX launcher** 没有可执行位，所以安装器测试的 `[ -x ]` 检查失败，POSIX 安装器套件从来没跑过。
- **Windows 安装器测试** 从环境里继承下载源而没有按用例固定，于是每个没有自己设变量的用例都在跑安装器当时恰好有的默认值上。**这一条是这一轮自己造成的**：把默认下载源改掉之后，所有没写明模式的用例就都挂了——而这本来就是一个测试该更早发现的。

另外有两个测试依赖 POSIX 信号：Ctrl-C 要能到达管道里的子进程，一次停止要是一个信号而不是一个退出码，否则会话分不清"停止"和"失败"。Windows 两样都没有，所以那两个在 Windows 上跳过。

**有三个测试测的是跑测的机器，而不是它们本该测的东西。** 这些是在 CI 绿到能反复跑同一批 job 之后才冒出来的，每一个都在繁忙的机器上失败，而它们说的那个行为其实完全正确：

- **登录页的小人在眨眼时瞳孔会越出眼白。** 瞳孔的位移是它自己宽度的一个比例，而眨眼把眼白的**高度**压扁却不改宽度，于是瞳孔中心在竖直方向上的余量几乎归零，而它被要求走的距离一点没变。现在每个轴各有各的余量，从当下画出来的眼白读出来，瞳孔被夹在余量里。这一条不是测试的问题：鼠标停在页面附近的用户是能看见的。
- **机器传输的测试**说两台机器上的两条命令会在 380ms 内跑完。那个常数测的是跑测的机器启动进程有多快。现在它拿并行的那次跟排队的那次比——同一台机器、同样的命令、相隔一瞬——两者的差别是一整个 sleep，再多的进程启动开销也吞不掉这个差别。
- **技能归档的测试**要造出故意超过限制的归档，而它在一台开发机上已经跑到 5001ms 了——套件 5s 的默认值是被险胜跨过去的。现在它自己拿到 30s，断言一个字没改。

**scope 换名了。** `@jiumate` 这个 scope 在 npm 上被别人占了，所以 31 个包改到 `@jadelau` 下。npm 不允许改已发布包的名字，所以这不是重定向，而是把**每一个写了包名的地方**都改一遍：每个 `package.json` 的 `name`、每一处 `import` 与 type specifier、每一条 `workspace:*` 依赖边、CI 与发布工作流里的 `pnpm --filter` 选择器、安装脚本里的一行安装建议，以及 Trusted Publisher 清单。有两处**看起来**像 scope、其实不是的，改名脚本对它们很小心：`@jiumate-builtin` 是插件 id 的后缀，`~/.jiumate` 是数据目录。

**三样拿不到的东西被去掉，而不是被假装。** 阿里云 OSS 镜像：GitHub Release 现在是唯一的分发点，默认下载源从 `auto` 改成 `github`，因为 `auto` 会先花一个来回去发现镜像不在。签名证书：没有密钥时签名的步骤会自动降级成未签名构建，这次发布就是未签名的。域名：站点现在伺服在仓库的 GitHub Pages 地址上，所以部署子路径是 `/jiumate/` 而不是域名根，每一个必须绝对的链接都跟着走——canonical URL、sitemap、robots.txt、一行安装命令，以及 App 自己的对外标识。域名与子路径是分开两个值，因为域名伺服在根、Pages 伺服在子路径，两者独立变化。

## 还差的：npm 上的 26 个包

`@jadelau` 下要发 26 个包：19 个插件加 agenthub、inspirations、pets、skins、core、server、cli。发布走的是 OIDC trusted publishing——没有 token，npm 通过 GitHub Actions 的身份认这个 workflow。

**现在发不出去，有两个原因，都不在代码里。**

第一，**OIDC 的 token 交换返回 404**。npm 那边给这些包配置的 trusted publisher 认不出这个 workflow，于是它退回到普通 token，而普通 token 这台机器上没有。

第二，**23 个包在 registry 上根本不存在**。npm 的 `PUT` 对一个不存在的包返回 404，而且 trusted publisher 只能配置给**已经存在**的包——npm 的设置页列出的是可以指向 workflow 的包，没发布过的名字不在那张表里。所以第一个版本只能用一次性 token 发出去，把包"种"在 registry 上，之后才能配 trusted publisher。

这三个包已经种上去了：`@jadelau/core`、`@jadelau/a2ui`、`@jadelau/agenthub`，版本都是 `0.0.0-stage`，描述是 *"Temporary package placeholder for staged publishing"*。剩下的 23 个还没有。

**怎么做**：`scripts/bootstrap-npm-publish.mjs` 就是为此写的，它按依赖顺序把 26 个包发一遍（插件先，因为 core 依赖它们；然后 agenthub；然后 core、server、cli），把 `workspace:*` 改写成真实版本号，并且只发一次。`--dry-run` 已经跑过，它认得全部 26 个包，也知道哪三个已经在了。

它需要一个**有 publish 权限的 granular token**，在 `NPM_TOKEN` 里或者 `~/.npmrc` 里。发完就撤销。

> npm 现在要求发布必须走 2FA：一个开了 2FA 的账号 + 一个 token，或者账号开 2FA + trusted publisher。这两条路都卡在同一个地方——token 得由账号持有的人建。

## 顺带发现的事

**这次发布改动了三个 tag。** `v0.4.0` 一开始打在 `dda2e5e` 上，那是 scope 改名之前、CI 全红的时候。它从来没有产出过 Release，所以把它移到当前的 commit 上是安全的——release.yml 里的 guard 本来就写着"版本对不上就 re-tag"。

**两个 pandoc 包的内部目录名不一样。** macOS 的归档根目录是 `pandoc-3.5-arm64/` 和 `pandoc-3.5-x86_64/`，Windows 与 Linux 的是 `pandoc-3.5/`。代码里三条路径写成了同一个，所以 macOS 的桌面构建每次都失败在一个明明在的文件上。现在路径按各归档的实际结构写，并且加了兜底：找不到就按名字去找，找到就记一条警告——Pandoc 换版本不该让整个发布停摆。

**Windows 桌面包的构建顺序反了。** installer 的 `build` 是发布路径，它要打 Windows 的 payload；而那个 payload 是 electron-builder 产出的，electron-builder 又在递归构建之后才跑。于是递归构建里 installer 提前跑了，对着还不存在的 payload 报错。现在它在 Windows 上也跟其它两个平台一样被排除在递归构建之外，等 unpacked 目录有了再单独构建。
