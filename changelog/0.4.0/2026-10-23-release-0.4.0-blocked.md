# 0.4.0 was ready to publish, but four external conditions were not in place

- **Date:** 2026-10-23
- **Type:** process
- **Scope:** `ci`, `tooling`

[中文版](2026-10-23-release-0.4.0-blocked.zh.md)

0.4.0's code, changelog and version numbers were ready and the tag `v0.4.0` was pushed, but the release did not complete: no Release on GitHub, no packages on npm, an empty OSS mirror. This entry records what was in the way, and why the things in the way were not in the repository and so could not be fixed by a commit.

> **What happened next (2026-10-27)**: three of the four are no longer problems. The account's spending limit was fixed, and the CI went green on its first run and the Release came out. The OSS mirror was removed rather than configured — the GitHub Release is the only download source now. The signing keys were never configured, so the installers ship unsigned. The one that remains is npm; see [0.4.0 shipped](2026-10-27-release-0.4.0-shipped.md). This entry stays because it records what was standing in the way the first time the release was attempted, and that is part of what this round is about.

## What the repository already had

- `changelog/0.4.0/` held all 32 entries of this round (in English and Chinese), and `RELEASE.md` was the body of the GitHub Release.
- The `version` in the root and in `packages/*` and `plugins/*`, and core's `VERSION` constant, were all 0.4.0 — the release workflow refuses a tag whose version does not match.
- `v0.4.0` was on `021ff2e`, and `RELEASE.md` was in that commit, so the workflow could read it.
- typecheck passed for five packages, the core/server/web/cli/desktop suites ran green locally, and the build artifacts came out.

## The four things in the way

**GitHub Actions' account spending limit.** From 2026-09-17 every workflow in this repository failed with the same message: *"The job was not started because recent account payments have failed or your spending limit needs to be increased."* Each job died within one to nine seconds, because it never started. The runs before 2026-09-17 still had 12 successes (`Deploy Site` and `CI`); after that, none. This is a matter of the account's settings, and it is not in the code.

**npm's Trusted Publisher was not configured for these packages.** The 0.3.0 release run (`34331535137`) got as far as `Publish to npm` and failed there: the OIDC token exchange returned 404, so pnpm fell back to a one-off token and `PUT /@linsight%2fagent-development` came back 404 from the registry. The reason is that the package does not exist on the registry yet — a Trusted Publisher can only be configured for a package that **already exists**. Neither `@prismshadow/jiumate-cli` nor its dependency chain is on npm today.

**The Windows signing key was not configured.** In that same run the desktop build wrote *"Missing EVSIGN_KEY secret required for Windows release signing."* The signing identity is in `packages/desktop/electron-builder.yml` and reads `NaisNet Technology Co., Ltd.`; the key itself is a repository secret, and it is not in the repository.

**The OSS mirror's environment was not configured.** The `mirror-oss` job complained `ALIYUN_OIDC_PROVIDER_ARN is not configured in the oss-production environment`.

## Found along the way

**0.3.0 was never actually published.** In its release run `check-release` passed, `Publish npm packages` failed, and the `release`, `desktop` and `Mirror GitHub Release to Alibaba Cloud OSS` jobs did not run at all. There is still no `v0.3.0` Release on GitHub; `release list` is empty.

**Nobody could install the software through the official channels.** The installers in the repository pointed at `https://jiumate.ooo/install.sh` and `https://jiumate-releases.oss-cn-beijing.aliyuncs.com`, but `jiumate.ooo` does not resolve in DNS and the OSS bucket answers 404 for `/`, `/releases/` and `/latest.json`. `penguin.ooo` still responds, but it serves the pre-rename installer, which points at a different GitHub repository.

**The tag was already pushed.** Once the account limit was fixed, re-running the same tag would do it — every step of the release chain is idempotent, and a version that already exists is skipped.

## Compatibility

No breaking change. This entry changes no runtime behavior; it records the state of the release.
