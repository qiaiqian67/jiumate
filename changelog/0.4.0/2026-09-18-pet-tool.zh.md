# 让智能体可以查看与控制桌面宠物

- **Date:** 2026-09-18
- **Type:** feature
- **Scope:** `core`, `server`, `web`

[English](2026-09-18-pet-tool.md)

新增 `pet` 内置工具，于是「关掉桌面宠物」「换成那只兔子」可以真的被执行，而不是只能被解释。这是参考实现那一整套能力里安全的一半：它只在用户已有的宠物之间做选择，凡是要写磁盘的都留给用户。

## 工具

- `action: "list"` 报出有哪些宠物、当前是哪一只；`action: "use"`（带 `pet_id`）切换到其中一只；`action: "show"` / `"hide"` 打开或关闭浮窗。
- `permission: "rw"`，因此变更会像其它写类工具一样走审批流，而不是被自动放行。
- **没有**暴露按路径导入和删除已安装宠物：两者都会写磁盘，仍留在 设置 → 应用。

## 宿主如何提供它

- 宠物是宿主界面而不是文件，所以工具自身不持有状态：core 声明 `PetControlPort`（`list` / `setActivePet` / `setEnabled`），宿主通过 `CreateAgentOptions.petControl` → `EnvironmentServices.petControl` 注入。没有宠物界面的宿主什么都不注入，工具会如实说明，而不是抛一个 errno。
- 服务端基于宠物目录加 `ui_prefs` 行实现该端口，并沿用 `PUT /api/me/prefs` 所记录的 PATCH 语义，因此不会丢掉 `ui_prefs` 其它写入方的字段。
- 工具调用不携带用户——Session 属于 Project 而不是某个人——所以端口作用于**本机管理员**的偏好。那正是桌面端登录的账号，也就是拥有宠物浮窗的账号；同时它也是智能体通过本地 API token 本来就具备的权限，因此这个工具没有扩大它的能力范围。
- 内置预设表移入 `@prismshadow/jiumate-pets`，因为服务端必须能说出用户可以切换到哪些宠物，而预设对它的磁盘目录是不可见的。只有 web 包的 URL 形状仍留在 web 端。
- 这样写入的偏好会以 `prefs_changed` 在用户事件流上广播；web 端（它持有唯一的 `EventSource`）再转发出去，宠物 store 重新读取，于是已经打开的浮窗会立刻跟随，而不是等到刷新。

## 兼容性

- 没有新增偏好，也没有数据迁移。
- 默认工具配置里新增了 `pet` 条目，但已存在的智能体其持久化的 `tools.builtin` 列表是按原样冻结的：本次变更之前创建的智能体，需要手工把该条目加进它的 `system_config.yaml` 才会拿到这个工具。这是所有新增内置工具的既有行为，不是本次引入的。
