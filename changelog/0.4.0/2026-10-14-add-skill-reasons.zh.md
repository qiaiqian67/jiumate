# "没有添加任何技能" 现在说明原因

- **Date:** 2026-10-14
- **Type:** fix
- **Scope:** `web`

[中文版](2026-10-14-add-skill-reasons.zh.md)

通过 URL 添加技能失败时，用户看到的是一句**不含任何信息**的话，而服务端
已经把答案算好了。

客户端只在服务端返回 **201 且 `added` 为空**时才发这句话。所以压缩包是解开
了的（解不开是 404，服务端日志里是 `201 19099ms`），而每一条写入都抛了错。
服务端为每一条在 `result.failed` 里记了 `reason`，客户端在紧接着的「部分
成功」分支里一直在用这些 `reason`，却在这个「全部失败」分支里把它们丢掉了。

**恰恰是那个解释「为什么现在磁盘上什么都没有」的分支，什么都没说。**

现在会说出来：`没有添加任何技能：<name>（<reason>）`；只有服务端确实没给出
任何原因时才回落到原来那句话，所以这条消息不会出现「冒号后面什么都没有」
的样子。

## 根因没有找到

对着真实路由、用 `/archive` 复现（它和 `/url` 走同一条解析-写入路径）：我试
的两种压缩包形状——`<skill>/SKILL.md` 和
`<repo>-main/.agents/skills/<name>/SKILL.md`——都返回 201 且 `added` 非空，
directory 路由和现有的 48 个测试同样正常。所以压缩包形状不是原因，写入路径
也不是。

没有继续往下猜：从两行症状去推测一个文件系统层面的失败，正是把错误的修复
推上生产的做法。

这次改动是找到它的前提——原因现在显示在屏幕上了，所以下一次尝试会自己报出
自己。
