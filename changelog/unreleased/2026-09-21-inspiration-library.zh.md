# 灵感库：内置案例，加上管理员自己写的案例

- **Date:** 2026-09-21
- **Type:** feature
- **Scope:** `@prismshadow/linsight-inspirations`（新增工作区包）, `packages/server`, `packages/web`

[English](2026-09-21-inspiration-library.md)

原来的「灵感库 / Inspiration」页是一个写死的清单：十一个案例放在一个 TypeScript 数组里，三个分类放在 i18n 字典里，没有任何添加的入口。现在它是一个真正的库——内置案例，加上管理员自己写的案例，按管理员自定义的分类归档，带封面、预览、收藏与搜索。

## `@prismshadow/linsight-inspirations`——新增工作区包

案例格式、字段上限、磁盘目录与内置预设。一个**案例**就是一个起点：一段填进输入框的提示词，以及这段提示词要跑在什么之上——建议的智能体、要预选的技能、它依赖的工具，以及可选的封面图与预览文档。

- **三个入口。** `.` 是 Node 入口（schema、路径、IO）；`./presets` 是内置清单，`./schema` 是类型、上限与 id 规则——后两个是纯的，因为 web 产物会引用它们，不能把 `node:fs` 一起拉进来。web 的 `node-free-imports` 测试会守住哪个入口允许在浏览器里用。
- **一个案例就是一个目录**：`<数据根>/inspirations/cases/<id>/case.json`，有封面或预览时再加 `cover.<ext>` 与 `preview.html`。分类则一个文件一个，放在 `<root>/inspirations/categories/<id>.json` 下，所以调一次顺序不是重写整个集合。与宠物、主题两个目录同形，理由也一样：这是用户自己写的内容，数据库仍然只放索引与聚合。
- **每个用户可见的字符串都是一对**：`title`/`titleZh`、`description`/`descriptionZh`、`prompt`/`promptZh`——沿用应用其他地方双语数据的扁平双字段约定。校验会把缺失的一侧用存在的一侧补上，所以只用一种语言写的案例在两个界面里都读得出来，而不是显示一张空卡片。
- **案例的 `kind`** 就是卡片角标上的字：`app`、`agent`、`skill`、`tool` 或 `prompt`。
- **id 一律小写 kebab-case。** id 同时是目录名，两半清单用同一套字符集，才不会在大小写不敏感的文件系统上把只差大小写的两个 id 撞在一起。十一个内置案例随之改名（`rhythmRunner` → `rhythm-runner` 等）；旧 id 只是 React key 和字典 key，从未落盘。
- **写入严格，读取只容忍两处。** 未知字段、超长、id 与所在目录不一致，一律拒绝。清单解析不了的案例被跳过并记一条诊断，而不是让整个清单读取失败；指向已不存在分类的案例保留自己的 `categoryId` 并记一条诊断——画廊的「全部」页签仍然看得见它。
- **封面文件名必须是单个路径片段且扩展名是已知图片类型**，MIME 由扩展名推导而不是照抄清单：类型是浏览器唯一会照着做的字段，而一个把 `.svg` 声明成 `image/png` 的清单会让资源路由用位图类型发矢量图。
- **内置清单就是原来草稿页写死的那十一个案例**，文案从 `packages/web/src/lib/strings{,-en}.ts` 搬到了案例自己身上。它们全部使用 emoji 字形封面，因为内置案例没有目录，图片无处可读。

## `packages/server`

- **`/api/inspirations`**——`GET` 返回合并后的清单（内置案例 + 管理员案例）、分类、读者的 `canManage`，以及读取过程中收集到的非致命诊断。`/cases` 与 `/categories` 上的 `POST`/`PUT`/`DELETE` 需要管理员，403 响应体与管理员用户路由一致。
- **`GET /api/inspirations/:id/preview`** 以 `text/html` 返回预览文档；**`GET /api/inspirations/:id/asset/:name`** 返回封面。两者都是只读，且只接受校验过的单个路径片段，这正是构造出来的文件名走不出案例目录的原因。
- **内置案例不能被替换或删除。** 内置案例随包发布、没有自己的目录，而 web 产物里的那份与服务器返回的那份唯一可能不同的只有管理员那一半——所以合并就是拼接，不存在「覆盖」需要推理。与内置主题同一条规则。
- **分类完全归管理员，包括产品自带的三个。** 它们是种子数据：`seedInspirationCategories` 只往「从来没有过分类目录」的库里写一次，之后就只是普通文件。判定依据是目录不存在而不是标记文件，这正是删除能生效的原因——只要这个库曾经有过分类，就永远不会被重新填充。改名、调序、删除，对它们和对自建分类完全一样。
- **正在被使用的分类不能删除**，拒绝时会说清下面还有几个案例。把它们改派或孤立，要么移动了管理员没提到的案例，要么让它只剩「全部」页签可达，这两件事都不该由一个删除按钮悄悄决定。这条检查也正是内置案例不会被孤立的原因。
- **封面以 base64 放在新建/更新请求体里**（`coverUpload: { filename, dataBase64 }`），因为该路由的写入契约是 JSON，而图片没有别的文本表示。`previewHtml` 用一个键表达三种意图：字符串写入预览，`null` 移除预览，不带这个键则保留磁盘上原有的。
- **`PUT /api/me/prefs` 新增 `inspirationFavorites`**——用户收藏的案例 id。写入时由 `services/inspiration-favorites.ts` 限制数量与 id 形状，与 `draftShortcuts` 同样的处理、同样的理由：`ui_prefs` 只有一个自由格式的 JSON 列。只做限制不做解析，因为内置案例没有目录，而在另一台机器上被删掉的案例不该让偏好写入失败。

## `packages/web`

- **页面变成画廊。** 页签是 全部 / 精选 / 每个分类一个 / 我的收藏，搜索框按标题、描述、提示词、技能与工具过滤，**两种语言都匹配**；卡片带封面、类型角标与「官方」角标。`/app-center` 路径不变——侧边栏入口、书签、草稿页的「浏览全部」都指着它。
- **详情弹窗用沙箱 iframe 预览案例。** `sandbox="allow-scripts"` 且**不带** `allow-same-origin`，文档落在一个唯一的不透明源里：脚本能跑，但读不到本应用的 Cookie 与存储，够不到父文档，自己的请求也是跨源的。这就是管理员写的文档的边界，也是服务端原样存储这段标记、不做改写的原因。
- **管理员编辑器**可以从表单新建案例，也可以改已有案例——一个弹窗，因为字段与规则完全相同。id 字段在新建时跟随名称，编辑时只读（它是目录名）。删除不在弹窗里：破坏性动作属于那行点名了「删什么」的控件，卡片上已经有了。控件一律用 `sm` 档，也就是新建智能体弹窗与 MCP 服务器表单那一档，所以字段尺寸和其他弹窗一致。
- **三个引用字段都是选择器，不是输入框。** 建议智能体是项目智能体的下拉，存的是 id；预选技能是内置技能库之上的共用多选面板；依赖工具是同一个面板，数据来自所选智能体真实拥有的工具（内置工具表 + MCP Server 名），没指定智能体时回退到当前智能体，列表不会无缘无故为空。
- **封面的方框本身就是上传控件**——一个包住文件输入框的 label，与本应用其他所有上传控件同形；旁边的字形输入是「不用图」的备选。
- **分类管理里每个分类都能编辑。** 产品自带的三个与自建的一起列出、一样可改，逐个带新建/改名/调序/删除；列表与表单是同一个弹窗的两个阶段，沿用快捷指令编辑器的写法。
- **收藏存在 `ui_prefs` 里**，按账号而不是按浏览器，沿用「已处理」标记的先例——收藏表示某个人挑了什么，共用一台工作站不该替同事收藏。写入是乐观的、整表覆盖的，因为 `PUT /me/prefs` 只在顶层合并。
- **清单只读一次，全局共用。** 模块级 store 以内置案例开场，所以草稿页的挑选器与页面其余部分在同一帧就画出内容，服务器结果到达后再换上。服务器读不到时降级为内置案例而不是空画廊，与主题选择器的降级方向一致。
- **草稿页的挑选器改为清单驱动**：每个分类一个页签，最多 `PICKER_ROWS` 行案例，再一行进入完整灵感库。上限是这块区域高度固定的原因——草稿页没有为它预留滚动区，而灵感库现在是开放的（管理员可以往里写）。用户自己的快捷指令保留独立页签、独立上限与独立存储。
- **「收进灵感库」**放在会话详情卡底部，仅管理员可见：用会话的开场提问与标题预填画廊用的同一个编辑器。中英两个字段填同一段文字，因为应用无从知道这段会话是用哪种语言进行的；会话用过的技能与工具刻意**不**带过来，那记录的是这次运行碰过什么，而不是案例需要什么。
- **两个字典里的 `S.chat.exampleTasks`、`S.chat.exampleFolders` 与 `S.chat.appCenter` 已删除**；内置案例的文案归包所有，页面 chrome 放进新的 `S.inspiration` 组。

## 未包含

- **案例包的导出与导入。** 格式本身就是一个目录，所以 `.zip` 往返是显而易见的下一步——它需要 `packages/skins/src/zip.ts` 已经做过的压缩包加固，以及一个共享数据根还提供不了的理由。
- **自动安装案例依赖的工具。** 案例声明的工具只以标签形式展示，绝不自动接线：声明工具是在说这个案例预期有什么，替用户装上 MCP 服务是应用替他们做配置决定。
- **编辑或隐藏内置案例。** 产品自带的十一个案例保持只读，与内置主题一样；管理员想要另一个版本就自己写一个。
