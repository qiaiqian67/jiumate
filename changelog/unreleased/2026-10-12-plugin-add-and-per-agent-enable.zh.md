# 插件变成本机对象：添加，然后按 Agent 启用

- **Date:** 2026-10-12
- **Type:** feature
- **Scope:** `core`, `server`, `web`, `skills`

[English](2026-10-12-plugin-add-and-per-agent-enable.md)

九川是一个本地客户端，没有市场可供下载，而插件页却当它有：在已经列着本机插件的卡片上，提供了一个「下载到本机」的按钮。这次改动让插件模型与产品本身对齐——插件是你**添加**到这台机器上的，一次即可，来源是 URL、压缩包或本地目录，然后**按 Agent 开启或关闭**。

## 添加插件

- **三个来源，一个对话框。** `/discover` 在写入任何东西之前预览一个仓库或压缩包；`/url` 从 git URL 导入，`/archive` 从上传的 zip 导入，`/local` 从本机目录导入，`/local/batch` 从含有多个插件的目录导入。仓库 URL 被解析成可获取的归档与插件名（`resolveRepoUrl`、`looksLikeArchive`、`pluginNameFromRepo`）。
- **添加的副本与同名的内置副本分开保存。** 用户插件安装为 `<name>@local`，内置库发布为 `<name>@jiumate-builtin`。安装按 id 寻址，因此二者可以各自安装、升级、移除，互不触及。`resolvePluginId` 负责选定 id：添加的副本优先，所以用户带来的就是用户用的；而只有内置的名字正好解析为 `builtinPluginId`。
- **添加一个目录会导入其中全部插件，并让它们对每个 Agent 都保持关闭。** 十次文件系统写入不应该顺带改变 Agent 当前能做什么。
- **压缩包经过加固与校验。** `unpackPluginArchive` / `writePluginArchive` 拒绝会逃出目标目录的条目，并剥掉唯一一层包裹根目录，避免插件比清单读取器预期的多嵌一层。

## 按 Agent 启用

- **开关是一个字段，不是一次删除。** `POST /api/skills/plugins/enabled` 改写 Agent 插件清单里的 `enabled`。关闭的插件不为下一次会话的提示词贡献任何内容，文件留在磁盘上，重新打开也不需要重装。因为一个正在运行的会话是在插件还开着的时候组装提示词的，切换时会同时让运行时失效。
- **开关只出现在当前 Agent 已安装的插件上。** 对不存在的东西的开关无事可做。
- **捆绑技能继承其插件的关闭状态。** 它的文件就在插件目录里，因此没有第二个可能失去同步的开关。

## 捆绑技能住在插件内部

插件的技能被安装到 `plugins/<name>@<marketplace>/skills/`，而不是在安装时被复制到扁平的 `skills/`。这样换来的是：

- **归属是结构性的。** 一个技能来自哪个插件由文件所在位置回答，因此它不可能出错，也不会因为某个写入者忘了记录而丢失。`InstalledSkill.plugin` 变为 `SkillMetadataItem.plugin`，而 `buildInstalledSkillsView` 显式排序它的三个来源——`structural`（技能位于某个插件的树内，直接胜出）、`recorded`（`installs.json` 指明了归属）、`inferred`（从当前存在哪些技能推断）。`inferred` 对结构性声明现在为 false：路径推导出的归属不是猜测，把它报告成猜测会让界面对自己已知的事情含糊其辞。
- **捆绑技能没有单独的移除路径。** 唯一能触及它的操作会连同插件一起移除它，于是「捆绑技能不可单独卸载」不再是界面上的一条规矩，而变成了这个布局的固有性质。因此卸载是插件层级的一次请求，而不是每个技能一次 DELETE——后者对捆绑技能已经变成空操作，它会报告成功却什么也没删掉。
- **关闭状态得以保留。** 关掉插件保留它的文件，重新打开不需要重装。

## 归属、迁移与对账

- **旧扁平布局下安装的技能会从两棵树里读取。** `listInstalledSkills` 同时读取 `skills/` 与插件树，因此这次改动之前的安装继续可用。
- **`migrateFlatBundledSkills` 依据库成员关系迁移，而不是依据已记录的安装。** 它曾从 `.installs.json` 查询每个已安装插件带来了什么，但那个文件对在该文件发布之前做的每一次安装都不存在——于是恰恰在最需要迁移的那些机器上，它什么也没点名、什么也没移动，而且悄无声息。现在它只在**恰好一个**库插件发布同名技能时才移动一个扁平技能，这是证明而非猜测。零个认领者留下用户自己的技能不动；两个或更多则属歧义，因此原地保留并上报。对真实数据根运行的结果是：9 个插件下的 18 个技能被移动，没有丢失任何一个。
- **迁移会写入清单与来源记录。** 没有清单，被迁移的插件就有技能却没有 `enabled` 字段，于是开关会在全新安装上正常，而在升级过的安装上静默无事——这是最糟的分裂。版本被留空而不是猜测：磁盘上就是已安装的副本。已有清单永不被覆盖。
- **`reconcilePluginIds` 在读取时运行，且是单向的。** 在添加 id 修复之前安装的机器保留着两个目录，于是 Agent 会提供两份插件，关闭只关掉其中一份。对账会把插件移向添加的 id，尽力而为，且绝不以牺牲用户设置过的技能或开关为代价。

## 从别处读取一个插件

- **优先读取 `.claude-plugin/plugin.json`；`plugin.json` 继续支持。** 这个顺序是刻意的：同时带两个文件的目录，是一个上游插件旁边放了我们自己的旧文件，而上游那份才是关于它是什么的权威陈述。一个能就自己的版本与自身产生分歧的插件，比任何一种布局都更糟。
- **分类是数据。** 插件根旁的 `marketplace.json` 覆盖随包发布的 `PLUGIN_CATEGORIES` 列表，后者成为兜底——于是我们从未见过其分类的插件无需发版即可归档。一份格式错误的文件会抛错，而不是悄悄重排用户没有改过的库。

## 卡片操作

市场源已移除；它们是一个没有网络事实来源的产品里的网络概念，而它们需要的每一条文案都得维护两种语言。卡片上的操作是那些在本地真正有意义的：

- **启用 / 关闭**，针对当前 Agent
- **从本机卸载**——不可逆，并且点名会失去访问权的那些 Agent，于是这条警告是用户能据以判断的
- **升级**，当存在更新版本时
- **管理标签**，与技能页共用

## 技能页归档

技能页签此前有一个分类*管理器*——新建、改名、删除——却没有任何把技能归档进去的东西，也没有任何按分类过滤的东西，于是这个功能是一个什么也不做的设置对话框。现在两半都在了：

- **`filings`（`itemId` → 分类 id，按用户）存放在自己的 `localStorage` 文件里**，与分类列表分开，这样分类改名不会重写每一份归档，而指向已卸载条目的归档会变成不可读而不是悬空。
- **捆绑技能继承其插件的归档**，而已存的归档仍然优先，因此技能可以有意从插件的分类里被拉出来。「跟随插件」是一个独立选项，而不是折进「不分类」里——回到继承与选择没有分类不是同一个动作。
- **筛选片是与来源页签分开的另一行，不是合并。** 来源回答「它从哪来」，分类回答「它是干什么的」。计数是搜索与来源过滤之后按分类的，所以一个筛选片回答的是「我点了会得到几个」。

## 兼容性

这里有三种早于本次变更的行为，每种都直接陈述它做什么，而不加辩驳：

- **插件 id 是 `<name>@<marketplace>`。** 报告插件 id 的地方显示完整形式（`agent-tuning@jiumate-builtin`），因为那是技能实际所在的目录；查找的地方去掉后缀（`pluginNameOf`，现在住在 core 里并且是唯一定义）。以一个没有条目对应的名字作默认是不允许加载的。
- **此前被放在内置 id 下的已安装插件，在读取时会被对账到添加的 id 上**，尽力而为且单向。在有这项对账之前，卸载这样一份副本会以 400 失败，并且可能删掉同名的内置副本。
- **已有安装绝不会被破坏性迁移。** 无法确定归属的扁平技能原地保留。`scripts/check-migration.mjs` 对真实数据根运行迁移，并报告什么被移动、什么被留下、以及是否有任何东西丢失。
