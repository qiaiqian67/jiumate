# Let a program outside the Web App call an Agent

- **Date:** 2026-10-20
- **Type:** feature
- **Scope:** `server`, `web`, `docs`

[中文版](2026-10-20-agent-api.zh.md)

An Agent can now be exposed to programs outside the Web App. An owner opens the Agent's API tab,
turns the switch on, mints a key, and a program presents that key to run the Agent over HTTP. The
tab carries the exposure settings and the key list; the calling side is four routes under
`/amsp/v1`.

## The tab

- 启用 Agent API, 允许免密钥访问, 审批模式, 思考强度, 工作区, 并发上限 — each of them read back
  from the server rather than from what was sent. `open` in particular is forced to 0 while
  `enabled` is 0, so a tab that showed what it had asked for would show a setting the server does
  not hold.
- A key is shown once, at creation, in a dialog that says it will not be shown again. The server
  keeps only a sha256 of it, so the secret cannot be reproduced afterwards; the list shows a prefix,
  the creation time and the last use.
- Deleting a key takes effect on the next request that presents it.

## The calling side

- `POST /amsp/v1/projects/:p/agents/:a/sessions` creates the session and sends the first turn in
  one request, and answers `202` with the session id. A turn takes as long as the model takes, so
  the run continues on the server and the answer is read with `GET` or followed over SSE
  (`GET .../sessions/:id/stream`) — the same split the Web App itself uses.
- `GET /amsp/v1/projects/:p/agents/:a/sessions/:id` answers the session's status and its messages.
- `DELETE /amsp/v1/projects/:p/agents/:a/sessions/:id` cancels a run in progress.

## What a caller does not get to choose

The model and the approval mode come from the Agent's own settings and are not read from the
request body. A caller that could pick its own model would run the Agent on a cheaper one than the
owner granted, and one that could pick its own approval mode would start turns under a laxer
policy. A caller may narrow the Workspace, and may set the thinking level.

## The refusals

- A key that matches nothing is `401`.
- An Agent that is not exposed, and an Agent that does not exist, are the same `404`. A different
  status for the two would make the endpoint an oracle for enumerating what exists on the server.
- A key minted for one Agent gets that same `404` when aimed at another, rather than being told
  it is real but points elsewhere.
- The admin's server-wide switch is `503`, not `404`: every exposed Agent is unreachable, and a
  `404` would send the caller to check an Agent name that is perfectly fine.
- Every slot busy is `429` with a `Retry-After`.

## Concurrency

The ceiling is per Agent rather than per key, and it is read on each acquisition, so lowering it
takes effect on the next run. The slot is held for the duration of the run and not the duration of
the request: a ceiling that only bounded the moment of starting would admit unbounded concurrent
runs, which is the thing it exists to prevent.

## What the rows follow

The settings row and the key rows are dropped with the Project that owns them, and the key rows
are dropped with the user who minted them. A key that outlives its Agent is a live credential for
something that no longer exists, and a key that outlives its owner holds the account hostage on
the foreign key.

## Where it is mounted

The calling side is mounted on the runtime, above the platform seam, with the other
runtime-owned surfaces. It is a mechanism surface — it authenticates a key rather than a session —
and the business routes are served by the platform bundle, which in a running installation is
whatever was pushed last. It is served on both loopback names: the preview host exists so that
Agent-written preview HTML cannot spend the user's session on the App's own API, and this surface
is not cookie-authenticated.

## Compatibility

- Two tables were added. No existing data is read or rewritten by them.
- The Agent's `tools.builtin` list is unchanged, and no Agent gains a tool: this surface is
  reached over HTTP by a program, not by the Agent itself.
