# The inspiration library: built-in cases plus the ones an admin writes

- **Date:** 2026-09-21
- **Type:** feature
- **Scope:** `@prismshadow/jiumate-inspirations` (new workspace package), `packages/server`, `packages/web`

[中文版](2026-09-21-inspiration-library.zh.md)

The 灵感库 / Inspiration page was a hard-coded catalog: eleven examples in a TypeScript array, three categories in the i18n dictionaries, and no way to add anything. It is now a library — the built-in cases plus the cases an admin authors, filed into categories an admin defines, with covers, previews, favourites and search.

## `@prismshadow/jiumate-inspirations` — new workspace package

The case format, its bounds, the on-disk catalog and the built-in presets. A **case** is one starter: a prompt to fill the composer with, plus what that prompt is meant to run against — a suggested Agent, skills to preselect, tools it expects, and optionally a cover image and a preview document.

- **Three entry points.** `.` is the Node barrel (schema, paths, IO); `./presets` is the built-in catalog and `./schema` is the types, bounds and id rule — both pure, because the web bundle imports them and must not pull in `node:fs`. The web app's `node-free-imports` test enforces which one a browser-safe import may use.
- **A case is a directory**: `<root>/inspirations/cases/<id>/case.json`, plus `cover.<ext>` and `preview.html` when it has them. Categories are one file each under `<root>/inspirations/categories/<id>.json`, so reordering one is not a rewrite of the set. Same shape as the pet and skin catalogs, and for the same reason — this is content a user authors, and the database stays reserved for indexes and aggregates.
- **Every user-visible string is a pair**: `title`/`titleZh`, `description`/`descriptionZh`, `prompt`/`promptZh` — the flat two-field convention the rest of the app uses for bilingual data. Coercion fills a missing side from the side that is present, so a case authored in one language reads as that language in both UIs rather than as an empty card.
- **A case's `kind`** is what its card badge says: `app`, `agent`, `skill`, `tool` or `prompt`.
- **Ids are lowercase kebab-case.** An id is also a directory name, so one charset for both halves of the catalog means a case-insensitive filesystem cannot collide two ids that differ only in case. The eleven built-ins were renamed accordingly (`rhythmRunner` → `rhythm-runner` and so on); the old ids were React keys and dictionary keys, never persisted anywhere.
- **A write is strict, a read is tolerant in two places.** An unknown field, an out-of-range length or an id that disagrees with its directory is refused. A case whose manifest will not parse is skipped with a diagnostic rather than failing the whole catalog, and a case naming a category that no longer exists keeps its `categoryId` and gains a diagnostic — the gallery's "All" tab still shows it.
- **A cover name is a single path segment with a known image extension**, and the MIME type is derived from that extension rather than read from the manifest: the type is the one thing the browser acts on, and a manifest claiming `image/png` for an `.svg` would have the asset route serve vector under a raster type.
- **The built-in catalog is the eleven examples the draft screen used to hard-code**, with their copy moved out of `packages/web/src/lib/strings{,-en}.ts` and into the case it belongs to. Every one of them uses a glyph cover, because a built-in has no directory for an image to be read from.

## `packages/server`

- **`/api/inspirations`** — `GET` returns the merged catalog (the shipped cases plus the admin's), its categories, the reader's `canManage`, and the non-fatal diagnostics the read collected. `POST`/`PUT`/`DELETE` on `/cases` and `/categories` are admin-gated with the same 403 body the admin user routes answer with.
- **`GET /api/inspirations/:id/preview`** serves the preview document as `text/html`; **`GET /api/inspirations/:id/asset/:name`** serves a cover. Both are read-only and named by a validated single path segment, which is what keeps a crafted name from walking out of the case directory.
- **A built-in case cannot be replaced or deleted.** The shipped cases live inside the package, have no directory, and the only thing that can differ between the web bundle's copy and the server's answer is the authored half — so the merge is a concatenation and there is no override to reason about. Same rule the built-in themes follow.
- **A category is the admin's, including the three the product ships.** Those are seed data: `seedInspirationCategories` writes them into a library that has never had a categories directory, and they are ordinary files from then on. The rule is the directory's absence rather than a marker file, which is what makes a delete stick — a library that has ever had categories is never repopulated. Rename, reorder and delete all work on them like on any other.
- **A category in use cannot be deleted**; the refusal names how many cases still hold it. Reassigning or orphaning them would either move a case the admin did not mention or leave it reachable only from "All", and neither is something a delete button should decide quietly. That check is also what keeps the shipped cases from being orphaned.
- **The cover is uploaded as base64 in the create/update body** (`coverUpload: { filename, dataBase64 }`), because the route's write contract is JSON and the image has no text representation otherwise. `previewHtml` distinguishes three intents on one key: a string writes a preview, `null` removes one, and leaving it out keeps whatever is on disk.
- **`PUT /api/me/prefs` gains `inspirationFavorites`** — the ids a user starred. Bounded on write by `services/inspiration-favorites.ts` (count and id shape), the same treatment `draftShortcuts` gets and for the same reason: `ui_prefs` is one free-form JSON column. Bounded but never resolved, because a built-in case has no directory and a case deleted on another host must not make the prefs fail to save.

## `packages/web`

- **The page is a gallery.** Tabs are All / Featured / one per category / Favourites, a search box filters on title, description, prompt, skills and tools in **both languages**, and the cards carry a cover, a kind badge and an official badge. `/app-center` keeps its path — the sidebar entry, bookmarks and the draft picker's "browse all" row all point at it.
- **The detail modal previews the case in a sandboxed iframe.** `sandbox="allow-scripts"` with **no** `allow-same-origin` puts the document in a unique opaque origin: its scripts run, but it cannot read this app's cookies or storage, cannot reach into the parent, and its own requests are cross-origin. That is what bounds an admin-authored document, and it is why the server stores the markup verbatim instead of rewriting it.
- **The admin's editor** creates a case from a form or changes one that exists — one dialog, because the fields and the rules are identical. The id field follows the title on a create and is read-only on an edit (it is the directory name). Delete is not in the dialog: a destructive action belongs on the row that names what it removes, and the card carries it. Every control is on the `sm` tier, the size the Agent create dialog and the MCP server form use, so the fields are the same size as every other dialog's.
- **The three reference fields are pickers, never free text.** The suggested Agent is a select over the Project's Agents and what is stored is the id; preselected skills are the shared multi-select panel over the shipped skill catalog; expected tools are the same panel over the tools the chosen Agent actually has (its built-in table plus its MCP server names), falling back to the current Agent when none is suggested so the list is never empty for no reason.
- **The cover box is the upload control** — a label wrapping the file input, the shape every other upload in this app uses — with the glyph field beside it as the zero-asset alternative.
- **The category manager edits every category.** The three that ship are listed and editable like any other, with add/rename/reorder/delete on each; the list and the form are two phases of one dialog, the idiom the shortcut editor uses.
- **Favourites live in `ui_prefs`**, per account rather than per browser, following the badge-dismissal precedent — a star says what one person has picked out, so a shared workstation must not star cases for a colleague. Writes are optimistic and whole-list, because `PUT /me/prefs` merges only at the top level.
- **The catalog is one shared read.** A module-level store opens on the bundled built-ins, so the draft picker paints its rows in the same frame as the rest of the page and swaps in the server's answer when it lands. A server that cannot answer degrades to the shipped cases rather than to an empty gallery, the same direction the theme picker degrades in.
- **The draft screen's picker is now catalog-driven**: one tab per category, at most `PICKER_ROWS` case rows, then a row into the full library. The cap is what keeps the block a fixed shape — the draft page reserves no scroll area for it, and the library is now unbounded because admins author into it. The user's saved shortcuts keep their own tab, their own cap and their own storage.
- **"Add to the library"** sits at the bottom of the conversation's details card, for an admin: the session's opening prompt and title seed the same editor the gallery uses. Both language fields are filled with the same text, because which language a conversation was held in is not something the app knows; the session's used skills and tools are deliberately *not* carried over, since they record what a run touched rather than what a case needs.
- **`S.chat.exampleTasks`, `S.chat.exampleFolders` and `S.chat.appCenter` are gone** from both dictionaries; the shipped cases' copy is the package's, and the page chrome is the new `S.inspiration` group.

## Not included

- **Exporting and importing a case pack.** The format is a directory, so a `.zip` round trip is the obvious next step — it needs the archive hardening `packages/skins/src/zip.ts` already has, and a reason to exist that a shared data root does not already serve.
- **Auto-installing a case's tools.** The tools a case names are shown as chips and never wired up: naming a tool is a statement of what the case expects, and installing an MCP server on the user's behalf would be the app making a configuration decision for them.
- **Editing or hiding a shipped case.** The eleven the product ships stay read-only, as the built-in themes are; an admin who wants a different version writes their own case.
