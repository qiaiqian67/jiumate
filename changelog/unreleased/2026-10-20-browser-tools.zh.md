# 让智能体读页面并在页面上动作

- **Date:** 2026-10-20
- **Type:** feature
- **Scope:** `core`, `server`, `desktop`, `docs`

[English](2026-10-20-browser-tools.md)

Agent 浏览器此前只以插件技能的形式存在，教模型去 shell 里调 `penguin browser`——而本仓库的 CLI 并不提供这个动词。所以产品里根本没有浏览器能力，只有"在别处用某个浏览器"的说明。

现在由两个内置工具驱动它。`browser_read` 报告后端与打开的标签页、打开 URL、关闭标签、把页面扫成简化 HTML 或纯文本，并把截图作为图像内容返回。`browser_act` 点击、输入，并在页面自身的源内运行 JavaScript。

## 读与写分成两个工具

- `browser_read` 是 `r`：它不替用户改变任何东西。
- `browser_act` 是 `rw`，所以点击、输入、脚本都要先过审批。点击能提交订单，脚本能读走 `document.cookie`。
- 合成一个工具、只带一个权限，就得让高频的读承担低频的写的分量。拆开之后，只想看一眼页面的模型完全不必进审批流，而点击仍然要问。

## 截图以图像本身回来

它通过 `ToolResult.images` 返回，模型在请求它的那一轮就看到页面。把截图写到磁盘再读回来，是同一张图，却要多花一次工具调用和一次往返。

## 后端由用户选，每次调用都说清是哪个

两个工具从不挑后端，每次调用都报告当前用的是哪个：��个以为自己读的是内置浏览器、实际读的是另一个的模型，会从长得一模一样的页面上得出错误的结论。标签页与用户共享，用户可以看着、也可以随时接管。

## 宿主提供什么，代码又不知道什么

这两个工具自身不持有状态，也不碰磁盘——它们调用宿主注入的 `BrowserPort`，而没有浏览器界面的宿主会如实说明，而不是失败。在 server 之下，一个实现支撑着一个 `BrowserLink`，它的对端可以是桌面端 shell，也可以是用户自己的 Chrome：差异由 `BrowserBackendCapabilities` **声明**，不是探测，所以接入第二个后端时它上面的一切都不用改。

桌面端 shell 把页面作为 `<webview>` guest 托管在主窗口里，并运行它们的 CDP——那只有主进程能做。它走的是 updater 与 PDF 导出器共用的那个 utilityProcess 消息端口，每个中继按 `type` 过滤自己的帧。

## exec 的守卫

`exec` 在用户已登录的页面里运行脚本，所以脚本运行期间该标签的请求会被拦截，离开该页面源的一律失败——这是在浏览器里强制的，不是靠读脚本来判断，因为藏在 `new Image().src` 里的调用能通过来源检查，在这里却同样会被拦下。无法拦截的浏览器会如实说明并拒绝该脚本，而不是不加保护地运行它。

## 兼容性

- 内置工具集新增两条，因此推进了内核：`KERNEL_VERSION` 现为 `2026-10-20`，工具页此前的默认 hash 移入 `KERNEL_SUPERSEDED_TAB_HASHES`。
- 主窗口的 `webPreferences` 新增了 `webviewTag: true`。它并没有扩大窗口能加载什么——每个 `<webview>` 仍要过 `will-attach-webview`，在本应用自己的浏览器分区之外一律被拒——只是允许 guest 挂载的位置。
- server 新增一个子路径导出（`@prismshadow/jiumate-server/browser`），承载 shell 与运行时之间的线路类型。
- 没有数据迁移，既有行为不变。
