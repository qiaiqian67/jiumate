# 让智能体读页面并在页面上动作

- **Date:** 2026-10-20
- **Type:** feature
- **Scope:** `core`, `server`, `desktop`, `docs`

[English](2026-10-20-browser-tools.md)

两个内置工具 `browser_read` 与 `browser_act` 驱动 Agent 浏览器：桌面应用的内置浏览器，或用户自己的 Chrome，由用户选择。`browser_read` 报告后端与打开的标签页、打开 URL、关闭标签、把页面扫成简化 HTML 或纯文本，并在同一轮里把截图作为图像内容返回。`browser_act` 点击、输入，并在页面自身的源内运行 JavaScript。

## 读与写分成两个工具

- `browser_read` 是 `r`。它不替用户改变任何东西，因此以只读走审批流。
- `browser_act` 是 `rw`，所以一次点击、一行输入、一段脚本都要经过审批。点击能提交订单，脚本能读走 `document.cookie`。
- 合成一个工具、只带一个权限，就得让高频的读承担低频的写的分量。拆开之后，只想看一眼页面的模型完全不必经过审批，而点击仍然要问。

## 截图以图像本身回来

`browser_read` 的 `screenshot` 通过 `ToolResult.images` 返回，模型在请求它的那一轮就看到了页面。把截图写到磁盘再读回来，是同一张图，却要多花一次工具调用和一次往返。

## 后端由用户选，每次调用都说清是哪个

智能体驱动哪个浏览器是用户的设置，两个工具都不挑。每次调用都报告后端，因为一个以为自己读的是内置浏览器、实际读的是 Chrome 的模型，会从长得一模一样的页面上得出错误的结论。标签页与用户共享，用户可以看着、也可以随时接管。

## 宿主提供什么

这两个工具自身不持有状态，也不碰磁盘。它们调用宿主注入的 `BrowserPort`（`EnvironmentServices.browser`），而没有浏览器界面的宿主会如实说明，而不是抛一个 errno。后端之间的差异由 `BrowserBackendCapabilities` **声明**，而不是探测，所以工具像运行时一样据此分支，而接入第二个后端时这里不需要改动。

## exec 的守卫

`exec` 在用户已登录的页面里运行脚本，所以脚本运行期间该标签的请求会被拦截，离开该页面源的一律失败。这是在浏览器里强制的，不是靠读脚本来判断，因为藏在 `new Image().src` 里的调用能通过来源检查，在这里却同样会被拦下。无法拦截的浏览器会如实说明并拒绝该脚本，而不是不加保护地运行它。

## Web App 面板所对话的界面

面板是应用窗口里的一个页面，而它是唯一能创建 `<webview>` 的东西——桌面端 shell 托管 guest，却不创建它们。所以浏览器的 HTTP 界面（`/api/browser`）就是"一个打开请求变成一个标签页"的地方：面板创建元素、拿到 guest 的 id、用它认领这个请求。没有浏览器界面的宿主回答 503 `browser_unavailable` 而不是 404：浏览器是宿主的一项能力，不是一个不存在的路径。

状态是**推**过来的，不是轮询的：一个标签页的出现、关闭或崩溃——以及一个被请求却还没有窗口来显示的页面——都在发生的同一刻，以 `browser_state` 事件送到用户频道。拉取（`GET /api/browser/status`）是给错过了推送的窗口补齐用的。所以标签条不会比智能体的页面慢一个轮询周期。

被认领的请求立刻离开待认领列表；而第二个窗口认领同一个请求会被告知它是重复的——它创建的元素会被移除，因为服务器不知道的标签页是用户回不去的页面。

## 一套关于地址的规则

用户在地址栏里打字，和智能体说"打开那个开发服务器"，说的是同一件事——所以只有一套规则，两边都走它：裸域名会补上协议（公网名用 https，回环地址和 IP 用 http），而词句变成一次网页搜索。智能体不必把 URL 拼全，而两边永远不会对同一个字符串有不同的理解。

## 等待，而不是反复扫描

`browser_act` 新增 `wait`：等某个元素出现或消失、等页面不再变化、等加载结束。页面自己盯着自己，所以一次调用就把等待做完了，条件一成立立刻结束。

这是最省模型预算的一个动作。一次真实页面的扫描要花掉几千 token，而一个不停轮询加载中的页面的模型，会把预算全花在轮询上。等超时会明说，而不是让模型自己去猜那个元素到底在不在。

`hover` 和 `upload` 也一起来了：很多组件只有悬停才显形，而文件输入框此前是 agent 根本填不了的东西。

## 智能体不只会点击和输入

`browser_act` 新增 `scroll`、`press`、`select`、`navigate`、`back`、`forward` 和 `reload`。滚动会回答页面最终到了哪里——动了没有、是不是到底了、页面多高——因为一个被告知"已滚到底"却其实没动的模型会一直问下去。按键是按人的键盘那样发出的，所以只接受可信事件的表单也会接受它。`<select>` 既可以按值选，也可以按用户看得见的文字选。

## 兼容性

- 内置工具集新增两条，因此推进了内核：`KERNEL_VERSION` 现为 `2026-10-20`，工具页此前的默认 hash 移入 `KERNEL_SUPERSEDED_TAB_HASHES`。`tools.builtin` 仍是上一版默认的 Agent 会推进到新版；被用户改过的则保留自己的行。
- 浏览器工具的动作集后来又长了一轮（`scroll` / `press` / `select` / `navigate` / `back` / `forward` / `reload`，以及 `url` 学会地址栏的规则），同一天复用同一个版本号，工具页此前的默认 hash 同样移入 `KERNEL_SUPERSEDED_TAB_HASHES`。
- 除此之外，既有 Agent 落盘的 `tools.builtin` 列表按原样冻结，与所有新增内置工具一样：本次变更之前创建的 Agent，需要手工把这两条加进它的 `system_config.yaml` 才会拿到它们。
- 主窗口的 `webPreferences` 新增了 `webviewTag: true`。它并没有扩大窗口能加载什么——每个 `<webview>` 仍要过 `will-attach-webview`，在本应用自己的浏览器分区之外一律被拒——只是允许 guest 挂载的位置。
- server 新增一个子路径导出（`@prismshadow/jiumate-server/browser`），承载 shell 与运行时之间的线路类型。
- 用户频道新增一个事件（`browser_state`），把浏览器的状态送到显示它的窗口。
- Web App 的 dock 新增一个 `browser` 面板，且只在 Electron 定义了 `<webview>` 元素的地方出现——桌面应用的主窗口。
- 没有数据迁移，既有行为不变。
