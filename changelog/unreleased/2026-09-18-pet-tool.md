# Let the agent inspect and control the desktop pet

- **Date:** 2026-09-18
- **Type:** feature
- **Scope:** `core`, `server`, `web`

[中文版](2026-09-18-pet-tool.zh.md)

A `pet` builtin tool, so "关掉桌面宠物" and "换成那只兔子" can be answered instead of explained. This is the safe half of the reference implementation's surface: it chooses among pets the user already has, and leaves anything that writes to disk to the user.

## The tool

- `action: "list"` reports which pets are available and which one is active; `action: "use"` (with `pet_id`) switches to one of them; `action: "show"` / `"hide"` opens or closes the floating window.
- `permission: "rw"`, so a change rides the approval flow like every other mutating tool rather than being auto-approved.
- Importing a package from a path and deleting an installed one are **not** exposed: both write to disk, and they stay with the user in Settings → Application.

## How the host provides it

- The pet is a host surface, not a file, so the tool owns no state: core declares a `PetControlPort` (`list` / `setActivePet` / `setEnabled`) and the host injects it through `CreateAgentOptions.petControl` → `EnvironmentServices.petControl`. A host without a pet surface injects nothing, and the tool says so rather than failing with an errno.
- The server implements the port over the pet catalog plus the `ui_prefs` row, keeping the PATCH semantics `PUT /api/me/prefs` documents so it cannot drop the fields of `ui_prefs`'s other writers.
- A tool call carries no user — Sessions belong to a Project, not to a person — so the port acts on the **local admin's** prefs. That is the account the desktop app signs in as and therefore the account that owns the pet window, and it is the same authority the agent already holds through the local API token, so the tool widens nothing.
- The built-in preset gallery moved into `@prismshadow/linsight-pets`, because the server has to be able to name the pets a user can switch to and presets are invisible to its on-disk catalog. Only the web-bundle URL shape stays in the web app.
- Prefs written this way are announced on the user event stream as `prefs_changed`; the web app fans that out (it owns the single `EventSource`) and the pet store re-reads, so an open window follows immediately instead of after a reload.

## Compatibility

- No new prefs and no data migration.
- A `pet` entry is added to the default tool config, but an existing agent's persisted `tools.builtin` list is frozen as written: agents created before this change do not pick the tool up until its entry is added to their `system_config.yaml` by hand. That is the documented behaviour for every new builtin tool, not something this change introduces.
